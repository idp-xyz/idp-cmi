# idp-cmi 安全评审（2026-11-10）

范围：idp-cmi 本身（认证、授权、SQL、连接器、配置与部署默认值），代码状态为评审开始时的 `main`。方法：读代码、对可疑点写**可复现的测试**去证明或证伪，不凭印象下结论。没有评审的：其他组件（HOST、Workspace、EER、idp-mcp、idp-sandbox 各有自己的边界）、渗透测试（依赖和标准库漏洞用 `govulncheck` 查过，见 F7）、真实流量下的拒绝服务。

## 已修复的问题

### F1 个人记忆的隔离（严重）
**证据：** 临时测试里，dan（只有 `cmi-reader`）用 `GET /v1/memory/records?scopeKind=subject&scopeId=carol` 列出了 carol 的记忆，用 `POST /v1/context/resolve` 带 `scope: {subject, carol}`（以及 `scopes` 数组）取回了同样的内容。之前的测试都只覆盖"默认作用域是自己的"，没有人**显式指定别人的作用域**。HOST/Workspace 的正常路径用成员自己的令牌、默认作用域，所以没触发；但任何能拿到 reader 令牌并直接调用 CMI 的人都能读同租户所有人的个人记忆。
**修复：** `mayNameScope`：别人的 subject 作用域只有 `cmi-writer`（写入它的服务，如 idp-host）或 `cmi-admin` 能指名；纯 reader 在列表和 resolve 里得到 403，按记录 id 读得到 404（不泄露存在）。对别人记忆的每一次读取都写审计 `memory.read_other`（谁、读了谁、经哪个入口）。测试：`tests/integration/isolation_test.go`。
**注意：** 这条是我们之前"记忆是私有的"那些验收（PATH E/F）**没有证明**的：它们验证的是"alice 默认看不到 bob 的"，不是"alice 指名也看不到"。

### F2、F3 连接器的出站请求
**证据：** `http-manifest` 连接器的 `baseUrl` 只要求以 `http://` 或 `https://` 开头；抓取用的是默认 HTTP 客户端（跟随重定向，不限地址）。`strings.HasPrefix(url, baseUrl)` 对 `baseUrl = https://docs.example.com` 放过 `https://docs.example.com.evil.example/…` 和 `https://docs.example.com@evil.example/…`（后者实际请求 evil.example），`/handbook` 也"包含" `/handbook-private`，`/handbook/../x` 逃出去。清单里的条目来自远端站点，是不可信数据，正是这道检查要防的。
**修复：** `cmi.URLWithin`（解析后比较协议、主机、端口，路径按段边界，拒绝凭据，路径清理后再请求）；连接器用的客户端 `ingest.NewHTTPClient`：不走环境代理、TLS 1.2 以上、**连接时**检查目标地址，非公网地址（回环、私网、链路本地含 169.254.169.254、CGNAT、保留段）一律拒绝（DNS 之后检查，所以解析到私网或 DNS 重绑定也被拒）；重定向最多三次且必须仍在 baseUrl 之下。运营方可以用 `IDP_CMI_INGEST_ALLOW_PRIVATE=true` 允许私网（开发或集群内文档源）。测试：`internal/cmi/urlwithin_test.go`、`internal/ingest/safehttp_test.go`、连接器集成测试里加了两条绕过条目。

### F4 文件系统连接器
**证据：** 任何租户的 `cmi-admin` 都能建 `filesystem` 连接器，路径只要求以 `/` 开头且不含 `..`，于是可以把服务器上任意目录里的 `.txt/.md/.json/.html` 读进自己租户的知识库；`WalkDir` 不下降符号链接目录，但 `os.Open` 跟随指向文件的符号链接。
**修复：** 默认**禁用**；运营方用 `IDP_CMI_FILESYSTEM_ROOT` 指定唯一允许的根目录，连接器路径解析符号链接后必须在其下，创建时（422）、同步时、读取时都检查；遍历时跳过符号链接，读取前再解析一次。测试：`TestFilesystemConnectorsAreConfinedToTheOperatorsRoot`、集成测试里的两条拒绝。

### F5 JWKS
**证据：** `IDP_CMI_JWKS_URL` 接受 `http://`（路径上的人可以提供自己的签名密钥，等于任意伪造令牌）；`JWKS.Key` 在刷新失败时无限期返回缓存的密钥，颁发方撤下的密钥在其端点不可达期间一直被信任。
**修复：** 启动时要求 `https://`，开发网络用 `IDP_CMI_ALLOW_INSECURE_JWKS=true` 显式放行（平台的 kind 与 compose 配置已加，并注明是开发）；密钥在颁发方不可达时最多再用 24 小时（`JWKS.MaxStale`）。测试：`adapters/identity/jwks_test.go`。

### F6 开发模式
**证据：** `IDP_DEV_MODE=true` 加 `IDP_DEV_SECRET` 接受共享密钥签的 HS256 令牌，可以冒充任何租户和角色；监听在任何地址都不报警。
**修复：** 非回环监听时拒绝启动，除非 `IDP_DEV_ALLOW_REMOTE=true`（会打警告日志）；CMI 自己的 compose 和 kind 冒烟配置已显式加上。

### F7 标准库漏洞
**证据：** `govulncheck ./...` 在本机 Go 1.26.8 下报告 10 个标准库漏洞，代码确实调用到（`net/http` 的 6 个、`crypto/tls`、`crypto/x509`、`mime/multipart` 各一等）。镜像是在宿主上用宿主的 Go 编译再放进 `scratch` 的，所以二进制里的标准库就是那台机器的版本；CI 的 `setup-go` 读 `go 1.26.0` 会选到有漏洞的旧补丁版本。
**修复：** `go.mod` 加 `toolchain go1.26.10`（`go` 会自动取这个版本，主机上的 `go build` 之后仍然是 `docker build --network none`）；复查 `govulncheck` 为 0；CI 新增 `govulncheck` 步骤，以后新出的漏洞会让合并检查变红。**其他仓库（idp-host、idp-workspace、idp-mcp、idp-sandbox）很可能同样如此，需要各自检查。**

## 未修复的问题，和为什么

**O1 线程、Agent、租户作用域。** `thread:<id>` 的记忆只受记录 ACL 保护；线程 id 是 128 位随机数，不可猜，但它会出现在运行记录、上下文包和日志里，拿到 id 的 reader 就能读那个线程的记忆。要真正解决需要给线程作用域一个所有者（谁创建的线程），这是模型改动，不是补丁；建议在 HOST 把线程所有者写进记忆的 ACL（`acl.subjects`），那样现有机制就能执行。租户与 Agent 作用域本来就是共享的，要保密的内容必须带 ACL。

**O2 强角色。** `cmi-writer` 可以读写任何成员的个人记忆（HOST 就是这样工作的），`cmi-admin` 可以做所有事。两者都不应授给普通成员，也不应授给用途很多的服务账号；本评审之后读别人记忆会留下审计，可以定期看 `memory.read_other`（HOST 每轮学事实会产生一条，量大时按主体聚合）。

**O3 连接器请求头。** 只禁止了 `Authorization`；`Cookie`、`X-Api-Key` 这类仍可配置，明文存在数据库并会返回给管理员。配置里已注明"不要放凭据，用反向代理"，但没有强制。

**O4、O5。** `/version` 只暴露版本号；PDP 的 `onError: skip` 在 PDP 不可达时放行，需要显式配置且默认是拒绝，只在确实要可用性优先时用。

## 检查过、没有发现问题的

SQL：所有取值都是参数；拼接进语句的只有常量、整数和用正则校验过的标识（`CreateVectorIndex` 的内存大小有格式校验；`EnsureLogin` 的角色名来自运维命令行）。全文查询：词项来自 `[\p{L}\p{N}_]+`，单引号加倍，最多 64 项。JWT：算法白名单（无 `none`，生产无 HS）、必须有 `exp`、校验 `iss` 与 `aud`、RSA 至少 2048 位。租户隔离：行级安全且对表所有者也强制，服务角色拒绝以超级用户或 BYPASSRLS 连接。日志：没有令牌、内容或查询进入日志。TLS：出站与监听最低 TLS 1.2。写入有限额（D34）、请求体有上限、幂等键按主体作用域。
