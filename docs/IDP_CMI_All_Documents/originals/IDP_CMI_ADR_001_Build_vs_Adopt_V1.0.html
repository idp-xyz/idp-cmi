0. 决策摘要（Executive Decision）

ADR-D01：采用「自主核心 + 成熟开源基础设施 + 适配器式算法组件」

  • BUILD（IDP 自主实现）：CMI Public API 与独立服务框架、领域语义和 Canonical Store、Source/Memory 生命周期与版本账本、权限治理与撤权可见性、Context Compiler、Adapter Contract、跨引擎迁移/索引投影控制、证据和上下文清单。
  • ADOPT（直接使用开源基础）：PostgreSQL、pgvector、PostgreSQL FTS、对象存储兼容 S3 协议实现；缓存使用 Valkey 或经许可证核对的 Redis 发行版。OIDC、遥测、队列等优先对接成熟组件而非自造协议。
  • EVALUATE（先评测再选择）：Hindsight 作为第一 PoC 引擎；Mem0 为同数据集对照。两者都尚未批准为生产主引擎。只让引擎成为派生记忆的候选生成和召回组件，禁止其独占规范数据与授权决策。
  • DEFER（条件成熟再做）：Graphiti/时序图投影、跨租户联合知识网络、专有向量集群、自学习治理、复杂反思控制循环。
  • REFERENCE ONLY（先参考，不直接绑定）：OpenViking 的上下文分层组织和按需加载。主项目为 AGPLv3；任何部署/分发/托管服务方式的采用先法务审查，并校验具体组件许可证。

主线技术决策不是“选 Hindsight 还是 Mem0”，而是“设计一个没有任何记忆引擎仍能完成安全读写、来源溯源和最小上下文编译的 CMI 内核”，然后把更智能的召回和反思作为增强组件接入。

决策要点（必须区分）

  1. 软件独立性：CMI 独立启动、鉴权、读写、健康检测不依赖 HOST/EER 或 IDP MCP Infrastructure。
  2. 数据权威性：CMI Canonical Store 为 IDP 记忆记录、生命周期及授权可见性的权威；EER 是其 Execution/Evidence 的权威；ERP/WMS/Parcel 等是其业务事实领域的权威。三者不得混同。
  3. 引擎可替换性：开源引擎可以拥有自己的内部索引、cache、mental models/banks，但只作为派生/候选状态；没有规范化映射、删除传播和索引重建能力，不批准生产化。
  4. 接口稳定性：HOST/EER 只依赖 CMI 的版本化契约；不直接调用具体引擎的 bank_id、Graphiti node/edge 或内部表。
  5. 安全性：不得因为召回服务不可用、缓存命中或图谱关系而绕过权限，且在当前来源撤权后必须阻断新内容暴露。
  6. 实现节奏：优先模块化单体 + 异步 worker，不先拆分多个微服务。避免复制 EER 的调度器、State Machine 及业务执行层。

1. 背景与真实问题

企业 Agent 常需要跨会话召回客户规则、历史异常和经验；但仅有向量库会遗漏时序、来源与权限，直接绑定单一记忆框架又使 HOST/EER 遭到版本、Schema 和许可锁定。IDP 已有 EER，且 HOST 被设计为无 EER 也可完成核心工作闭环。CMI 应支持这两者，同时成为可对外提供的独立基础设施。

成功不等于能回答“用户以前说过什么”，而是能在授权与业务有效时点下回答“本次任务应该得到哪些经过来源追溯的信息”，同时可以可靠撤权、审计、迁移与复现；仍由业务 SoR 返回事实并由 EER/获准业务服务执行动作。

不做：通用 Agent Runtime、LLM Serving、流程编排、业务副作用/补偿、作为 EER Evidence 唯一存储；也不另造一个 MCP Gateway/Registry/路由治理产品。

4. 逻辑与部署架构

部署 P0：cmi-api 单进程或单服务（可水平扩）、cmi-worker 异步任务、PostgreSQL+pgvector/FTS、获准的对象存储、可选缓存；记忆引擎为独立进程/容器，有单独 service credential 和禁止对公网直露的管理 API。单机 Docker Compose 可开发，生产 Kubernetes/独立虚机均可，但逻辑模块不等于要求微服务拆分。

4.1 与 IDP MCP Infrastructure 的关系（重要）

CMI 对外可提供直接 REST/gRPC API 和 标准 MCP Server 能力；IDP MCP Infrastructure 是独立 MCP 连接与治理产品，可选择代理 CMI 的 MCP Server，但 CMI 的独立部署、鉴权、读写、健康检查不得依赖它。MCP Infrastructure 不接管 Memory Lifecycle/数据授权；CMI 不重造 Registry、通用 Gateway 和 MCP Client/Host。

协议边界：针对 IDP 已定 2026-07-28 最新正式 MCP 基线，CMI MCP Adapter 仅面向 Modern Stateless 核心：每个请求带版本与能力元信息；HTTP POST；无旧式 initialize、会话或 Mcp-Session-Id 适配，不引入 Legacy Adapter。与标准 Server/Client 的兼容测试在协议层执行，但 REST/gRPC 业务能力与 MCP 无耦合。

避免误用：不因为 Hindsight 内置 MCP endpoint 就直接允许其暴露生产租户数据。必须通过 CMI Policy Enforcement 或经形式化验证能等价执行授权的代理层，且不得信任仅由请求给出的 bank_id。

5. Canonical vs Engine State：数据主权契约

5.1 三种数据必须分开

类别 权威持有者 举例 引擎崩溃处理
原始权威业务事实 Parcel/ERP/WMS/EER 各自业务域 当前运单状态；ExecutionRecord/Evidence 必须回源核验，不以记忆替代
CMI 规范记忆与来源账本 CMI Canonical Store SourceRecord、MemoryRecord/revision、授权、有效期、删除状态 CMI 仍可查询元数据/FTS；重建派生能力
引擎衍生状态 独立 Engine Store（非权威） bank/向量索引/内部知识图/反思模型 标记缺失并重建；安全回退/降级

核心挑战不只是同步复制两个数据库。**引擎提取的候选必须投递回 CMI 经统一规则验证、去重并写入 Canonical Store。**引擎侧自主产生的新事实、推断和修订若不经过 CMI，不得直接进入公共检索输出。

5.2 写管线（write ownership）

  1. 外部提交 SourceIngestRequest；CMI 自行校验身份、purpose、来源权限，创建 SourceRecord；禁止传入可直接生效的状态/权威度。
  2. Registry 与 transactional outbox 同事务提交 SourceAccepted；异步引擎可抽取 candidate claims；外部处理器只拿到合规最小材料。
  3. CMI 将 candidates 标准化，校验每个 claim 的 source_refs、租户和有效时间；检查与现有 claim 冲突、重复及适用范围。
  4. Policy + 规则（需要时人工审批）决定候选可否转为 active；源授权变化可以随时阻断可见性。CAS 写新 revision 与 outbox。
  5. Outbox worker 幂等投影 FTS/vector/可选图谱；记录 generation, projection_watermark, 失败重试与 Dead Letter。

一致性：CMI Registry 是事务锚点；衍生系统采用可观测的最终一致。engine_ack 是投影处理回执，不是事实获批或业务执行成功。

5.3 读管线（read ownership）

authn + purpose → effective ACL prefilter → FTS/vector/engine candidates → registry resolve by IDs → valid_time/known_at/scope/classification/current policy recheck → dedup/rerank → cite sources → Context Compiler packing。

引擎返回纯文本但无法可靠映射到规范 memory_id/revision/source_refs 的情况：不得以“可信历史事实”身份进入 ContextBundle。可作为独立 external_untrusted 建议经过约束后候选使用，或直接拒绝该引擎的生产接口。这个限制须写进 PoC Gate。

5.4 删除、撤权和迁移

  • revoke 必须以 CMI 主账本同步不可见开始，旧索引/引擎未删净不能继续外泄。
  • erase 清除原文、规范记录明文、向量、图、引擎 bank、缓存、可读 Bundle、派生摘要；向外引擎/供应商发出 delete request 并跟踪回执与法定例外。
  • 对引擎不支持删除某条 claim、只能删除整个 bank 的情况，必须证明 bank 粒度和租户/作用域的映射安全，或者以重建策略确保可验证的彻底移除；否则拒绝其生产资格。
  • 迁移时采用 canonical snapshot → 新引擎 projection → 双引擎影子召回（返回只以主链判定）→ 一致性/准确率验证 → 受控切换；禁止两个引擎竞争写同一记忆规范版本。
  • 保留“最小合法擦除 Tombstone”而不留存可重识别正文；加密备份/PITR 恢复必须经过撤权/擦除屏蔽重放，再重新对外提供服务。

8. 具体 PoC 方案：同数据集、同模型、同预算

8.1 三组被测方案

  • S0 Baseline：CMI Canonical Store + PostgreSQL FTS/pgvector + 最小规则检索，无专业记忆引擎。
  • S1：S0 + Hindsight Adapter（独立服务、锁定版本）。
  • S2：S0 + Mem0 Adapter（独立服务、锁定版本）。

相同的输入、授权身份、实体版本、tokenizer、embedding / LLM 可比配置、硬件与成本统计口径。某引擎需要不同模型时分两组报告：产品默认配置结果与尽可能控制变量的配置结果。所有选型都必须通过 S0 确认内核可以退化运行。

8.2 评测数据建议

构建 240 个任务样本（初始建议值，不是已经拥有的数据），包含正常记忆回忆、客户规则变更、冲突事实、跨多会话、时间点回溯、用户撤权/擦除、Prompt Injection、跨租户越权、Source 撤回、Parcel 地址/门牌/渠道异常、EER Evidence 来源引用和反思经验治理。每个样本由行业人员标注真值、必引来源、允许/禁止记忆、时序窗口、预期行为。分为公开合成与经审批脱敏真实数据；测评数据禁止用未经授权的客户生产数据。

8.3 必过安全/架构 Gate（任何一项失败不准入）

  • GATE-A1 主权：关闭/卸载所有外部引擎，CMI 可独立完成 canonical 读写、RLS/ABAC、基本检索及上下文编译；HOST/EER 无 CMI 仍能独立运行。
  • GATE-A2 语义：引擎结果可确定性映射回当前有效 memory_id/revision/source_refs；不能只有不透明答案文本。
  • GATE-A3 授权：跨租户、跨主体、撤权后、过期源的非授权明文输出为 0 次（在覆盖的测试中）；不承诺测试之外绝对无漏洞。
  • GATE-A4 删除：完成规范/引擎/索引/缓存/快照删除流程且保存可核验完成证据；不支持删除的引擎不得被选为生产插件。
  • GATE-A5 迁移：canonical → 新引擎重建可重复；切换中无失效旧内容重新变可见。
  • GATE-A6 合规：许可证、数据驻留、供应商调用及 SBOM 会签，缺失不可对外商用。

8.4 可加权比较的质量/成本指标（仅在所有 Gate 通过后）

指标 定义 建议权重 报告说明
Grounded recall@k gold 支持事实在可追溯结果中的覆盖 25% 在同召回预算下报告
Temporal correctness 双时态与冲突事实的准确判断 20% 与业务事件生效/登记时间分开
Context answer quality 基于固定 prompt 和 token 预算输出的正确性 20% 人工复核 + 可复验自动度量
P95 latency 用户可感知检索/编译延迟 10% 冷/热、租户规模和退化模式分列
Cost per 1000 tasks LLM、embedding、数据库、存储、基础设施 10% 不只计算 token
Delete/rebuild operability 删除/重建耗时、失败率、手工操作量 10% Gate 通过之外比较维护性
Upgrade/license/operations 上游版本变更、运维复杂度、合规开销 5% 审计打分并附证据

上表权重是待确认的选型政策建议，不是预先断言谁领先；性能上线阈值须依据真实工作负载基线与客户 SLA 制定，不虚构目前的 P95 毫秒值或收益百分比。综合分不能覆盖安全 Gate 的否决权。

8.5 结论分支（避免预设答案）

  • 若 S1 通过所有 Gate 且显著提升任务效果/总成本优于 S0，则选用 Hindsight 为 Version-pinned Engine Plugin。
  • 若 S2 优于 S1 且过关，则选用 Mem0。
  • 若两者有无法修复的删除/回溯/授权映射问题，则维持 S0，先自研有限的候选抽取/混合检索，暂不引入专业引擎。
  • Graphiti 只有在某些跨实体时序查询对 S0/S1/S2 带来经验证的明显新增收益时，进入下一轮试点。

12. 直接写入下一版 Technical Design 的接口清单

  • storage/canonical：SourceRecord、MemoryRecord revision、ContextBundle、policy_ref、source→memory→bundle 依赖表、tombstone/erasure_request、outbox_event、projection_checkpoint、engine_mapping。
  • domain/lifecycle：propose, transition(expected_revision), invalidate(source_ref), erase(op_id)，事务/重入/并发/重放状态机。
  • security：authorize(principal,purpose,action,resource)，read prefilter 与 post-check，RLS，token iss/aud/scope，Bundle read-time validation。
  • retrieval：search(query,valid_time,known_at,scope)，FTS+vector merge，candidate→canonical resolve，freshness & trust filter，ranker。
  • context：compile(task,model_profile,budget)，包预算、固定字段、来源引用、manifest 与 hash、不可把检索文本提升为 system 指令。
  • engines：EngineAdapterV1、capability matrix、HindsightAdapter、Mem0Adapter（仅 PoC）、rebuild/delete/ACK/telemetry。
  • adapters：HOST Context Consumer、EER Evidence/Event Consumer、CMI Modern MCP Server Adapter（均独立可选）。
  • test：schema、跨租户、时序、撤权、erase、migration、no-engine fallback、MCP 互操作、Parcel 回归。
