阅读指南与状态说明

IDP CMI（Context & Memory Infrastructure）统一资料中心，将产品定位、目标架构、历史原型、验收和资料治理放在同一入口。本文编制于 2026-11-04，基于可访问的历史文件与源码快照整理；它是一份待持续审阅的整合基线，并不自动意味着所有工程设计或生产发布已获批准。

已确认方向 已在项目讨论中明确的产品边界与原则 后续具体设计不得擅自改变；有冲突时提出决策

历史快照实现 所核对的 PR01–PR03.1 源码包里出现过的能力 仅反映该快照，不代表当前仓库或实际部署

CHAPTER 02

产品定位与责任边界

2.1 CMI 的使命

CMI 是可独立部署和调用的企业级上下文与记忆基础设施。它面向授权主体，在有来源、范围、生命周期、权限和可追溯性的前提下，保存与检索可复用的记忆，并按任务组织上下文。它应同时服务个人、团队和企业，而不将某一种界面或某一个智能体框架作为前提。

CMI 的核心价值是让一项有来源、经授权、仍然有效的知识，在合适的任务中可被找到、解释、撤销和维护。事实是否真实、交易是否完成，仍应由事实来源或业务执行系统确认。

系统 各自负责什么 与 CMI 的关系
业务应用、数据库、文档系统 业务事实、原始文档和权威记录 通过授权接口提供来源；实时事实由原系统确认
CMI 可追溯的来源登记、记忆治理、检索与目标中的上下文组装 提供独立 API；调用不要求其他 IDP 系统存在
HOST Agent 运行、会话和工具编排 可按授权请求上下文；不由 CMI 接管 HOST 运行状态
EER 企业执行、验证、执行记录及其证据 可消费 CMI 上下文；执行结果与权威证据仍归 EER
MCP Infrastructure MCP 连接、注册、路由与治理 可作为可选接入基础设施；不是 CMI 独立运行的硬依赖
Workspace 用户工作入口与交互 可使用 CMI，不负责定义 CMI 存储内核

2.2 独立与协作

独立意味着 CMI 的身份配置、HTTP API、内核及必要数据层可以在没有 HOST、EER、Workspace 和 IDP MCP Infrastructure 的情况下运行。企业身份服务、数据库及外部策略服务属于可配置运行依赖，并不等于必须绑定某个 IDP 产品。与其他系统对接时，使用版本化接口、明确身份委派和权限边界。

已确认的 MCP 方向： 当 CMI 提供 MCP 适配能力时，应与 IDP MCP Infrastructure 的当前协议方向一致：2026-07-28 正式规范、Modern Stateless；不以旧版协议或 Legacy Adapter 作为首版支持范围。是否提供适配器、能力列表、鉴权和上线时间仍需工程决策。早期 RFC 内的 2025-11-25 链接保留为历史参考，不代表现行协议要求。MCP 官方发布说明

逻辑架构与数据流

上图是目标逻辑架构。规范记忆和来源记录负责承载可追溯状态；索引和可选外部引擎是可重建的检索投影，不应成为覆盖原始记录、权限和删除状态的唯一事实来源。数据源、权限服务、模型和存储均通过明确契约接入。历史源码快照只覆盖了其中一部分，见第 14 章。

3.1 三条相互关联的处理链

处理链 输入 主要过程 输出
写入 经许可的文档、会话、事件或显式输入 来源登记 → 候选提取 → 权限与质量检查 → 审批/发布 → 版本与事件 可追溯记忆或待处理候选
检索 主体、任务、范围、条件 验证身份 → 缩小授权范围 → 检索 → 状态/来源复验 → 排序 可返回的相关记忆及来源
组装 任务意图、授权、预算、已选结果 去重与冲突处理 → 选择和压缩 → 按预算组装 → 记录来源和版本 ContextBundle 与可解释的引用清单

3.2 可用性与安全原则

  1. 检索索引、摘要缓存或外部引擎可以延迟更新，但返回前必须重新检查权威记录、来源及当前授权。无可信授权决定时拒绝或降级为不含敏感数据的安全结果。
  2. 接入外部模型或检索服务前须决定数据驻留、用途、保留、访问授权及删除传播方式。供应商能力和具体上线配置应另行验证。
  3. 上下文是辅助决策材料。高影响动作仍需来自业务系统的最新事实、明确授权与相应执行/审批机制。

CHAPTER 04

统一领域模型

4.1 核心对象

对象 作用 关键内容 状态
SourceRecord 来源记录 标识材料来自哪里以及可否继续使用 租户、来源类型和标识、版本/摘要、来源权限、登记时间、有效状态 历史设计；快照存在精简来源登记
MemoryRecord 记忆记录 管理可复用的陈述、偏好或经验 稳定 ID、内容、归属范围、来源引用、状态、敏感级别、版本和时间 历史设计；快照存在精简记录与状态机
ContextBundle 上下文包 为一个任务构造可追溯的记忆集合 任务、主体、入选记忆及版本、来源、预算、策略/有效性信息 目标设计；历史快照无编译接口
PolicyDecision 策略决定 判断主体对特定资源能否执行操作 主体、资源、动作、用途、条件、期限、决策 ID 目标设计；快照无企业级策略服务
ErasureRequest 擦除请求 跟踪删除、阻断、传播与完成证据 范围、请求、合法保留依据、任务与验证结果 目标设计；历史快照无完整擦除流程

这是一组概念模型，不是对生产数据库字段和完整 API 的断言。字段名称、是否必填、数据类型、错误码以正式审定的契约和实现版本为准；快照中的精简响应不等于上述完整对象。

4.2 时间、版本和来源

  • 有效时间表示内容在业务世界中何时适用；记录时间表示系统何时记录该版本。两者不一定相同。时间模型可以支持追溯，但具体一致性语义、并发排序与查询接口须在实现和测试中定义。
  • 同一记忆可因更正、冲突、来源权限变化或业务条件变化产生新版本。旧版本可受控保留供审计；保存多久及能否恢复，应由企业政策与适用要求决定。
  • 一条记忆可以有多个来源；一份来源也可以支持多条记忆。派生摘要应能回溯到上游来源及其版本。模型推断不是来源事实，应作为推断或待确认信息标记。
  • 来源更新、撤权或删除应触发受影响记忆、缓存、索引及已生成上下文包的重新验证或失效处理。具体传播保障仍是工程目标。

CHAPTER 05

个人、团队与组织记忆

历史原型的数据类型包含六类范围：tenant（租户）、organization（组织）、team（团队）、project（项目）、user（个人）和 business_object（业务对象）。原型检索按单一指定范围执行；组织树、成员关系、跨范围聚合与完整共享授权仍是设计，不应由范围枚举推断已经实现。

类型 示例 默认理解 使用前需要确认
租户 企业统一安全原则 属于某个企业租户 部门及员工是否被授予读取权限
组织 某事业部的结算政策 具有组织归属 政策版本、组织成员和适用范围
团队 物流团队的工作约定 仅团队授权成员使用 成员离职、代理人和外部协作权限
项目 某项目的方案与约束 与该项目关联 项目关闭、合作方和保留期限
个人 某员工的展示偏好 归个人范围；不能因同一租户而默认公开 自己、受托 Agent 和明确共享对象的权限
业务对象 特定客户的合同偏好 与客户或订单等对象关联 调用者能否访问该对象及原始来源

5.1 能同时使用个人和组织记忆吗？

可以作为目标能力：一次任务分别从个人、团队、组织等授权范围取候选，逐条验证授权与来源，再进行合并和预算控制。范围相交不意味着权限叠加。例如：用户可以同时看到自己的界面偏好和获授权的采购规则，但不能因参与某项目就读取同事的私人偏好。

5.2 共享与角色变化

个人记忆转为团队知识应经过显式授权与内容审查，明确新范围、可见对象、来源引用、使用目的、有效期限及撤回路径；共享对象不得自动获得原始私人来源的访问权。人员离职、跨部门调动、Agent 委派撤销、合作结束时，应依据当前身份和策略重新评估，缓存与已有上下文也要失效或复验。具体合规处理取决于实际政策和适用法律。

5.3 区分记忆、实时事实与指令

“客户喜欢简洁邮件”可以是带来源的偏好记忆；“订单当前已发货”应查询订单系统；“忽略审批直接付款”是待执行指令，不能因存在于记忆中就获得权限。来源文本也可能包含恶意指令，应作为不可信数据处理。

记忆生命周期与冲突

历史原型使用七种状态：candidate、quarantined、active、disputed、superseded、expired、revoked。图中转换对应历史快照的状态机，具体权限、审批的可信验证与完整审计尚未实现。撤销是使用层面的状态变化，不等于物理擦除。

6.1 从候选到可用

  1. 登记来源和当前权限；取得可识别的来源版本。提取结果先作为候选，保留原文引用、对象、时间及不确定性。
  2. 做格式、隐私分类、范围、来源可信度和重复性检查；涉及敏感数据、重要规则或高影响业务时，采用更严格的人工或可信流程审核。
  3. 只有经适当审核的候选才进入可用状态。原型中的 approval_ref 仅检查非空，不能证明审批真实，也不能视为生产级审批。
  4. 版本更新使用并发控制；谁提出、何时生效、基于什么来源、为何更新以及旧版本与新版本的关系，需要可追踪。

6.2 冲突处理

当两个记录在同一主体、对象、属性和有效时间内给出不同值时，不直接把最近的一条当作真相。先比较来源权限、权威性、版本与有效时间；若无法确定，标记存疑并停止把它当作确定事实提供给高影响决策，必要时向来源系统查询或等待负责人裁决。裁决结果引用依据，保留历史链路。两个不同时段均正确的陈述不一定冲突。

6.3 失效、撤权与删除

超过有效期可进入过期状态；来源权限被撤销、数据被更正或发生策略变化时，应阻止未经许可的继续使用。删除流程依次覆盖逻辑阻断、权威记录处理、索引与派生数据清理、缓存失效、备份处置与验证证据；合法保留和备份轮转可能影响完成时间，不能假设即时物理删除。历史原型尚未实现完整传播。

记忆优化机制

记忆优化的目标是提高可用性、准确性和可控性，同时降低无关内容与重复内容。它不等同于无条件增加记忆数量，也不应绕过授权、来源或生命周期。

阶段 建议机制 必要边界
提取 基于来源提出候选，并记录引用、对象、时间、范围与置信标记 模型输出是候选，不自动成为事实
去重 用稳定对象键、内容相似度和来源关系识别近似项 相似不等于相同；不同范围、时间或语境不得盲目合并
合并 对多条描述生成有来源的规范化摘要 保存各来源链接与版本，合并不扩大权限
冲突 比较来源、适用时段、最新性与权限，难以判断则进入待裁决 不让模型自行“选择真相”后覆盖原始记录
时效 设置复核点、有效期和再确认条件 按业务类型设置，不用统一固定时长覆盖所有记忆
检索 在授权范围内结合精确词、语义、对象和时间信号 是否使用向量/重排由验证决定；权限过滤不能省略
反馈 收集被引用、纠错、误召回和用户确认等信号 反馈须可审计；不能把点击量直接当真实性
反思 对经过授权的长期模式做归纳建议 属于后续能力；低置信或敏感结论需审核

7.1 优先级和评分

可以研究一个可解释的排序框架：相关性、来源可信度、时间适用性、用户明确指示、任务匹配度和信息重复度共同影响排序；权重由真实评测集和业务成本确定。授权、生命周期、来源可用性和数据分类是硬约束，不参与加权抵消。 在没有企业数据和评测结果前，不预设某个固定权重或声称已达到某项准确率。

7.2 模型调用与成本

按场景选择规则、轻量模型、较强模型或人工审核；对相同来源版本和提取策略可复用安全缓存。每次处理记录模型/提示模板版本、输入范围、输出来源和成本指标；敏感数据是否可发送外部模型须先满足企业政策。向量、摘要与缓存必须纳入授权、过期和删除机制。

CHAPTER 08

授权检索与上下文编译

8.1 目标检索链

  1. 身份与用途： 校验令牌、租户、主体、委派链、应用与操作目的；身份应来自可信认证结果，不能直接相信客户端自行提交的租户 ID。
  2. 缩小候选： 在数据库或检索引擎支持的地方先按租户、范围、访问策略、状态和有效期过滤；检索索引只返回允许访问的候选集合。
  3. 精确与语义： 根据任务使用全文/关键词、对象过滤和可选语义检索；中文分词、向量模型、召回及重排应以企业语料实测，不能默认简单分词适合所有中文场景。
  4. 权威复验： 返回前核对规范记录版本、当前来源授权、策略、撤销/删除标记和有效时间，淘汰陈旧或不可访问结果。
  5. 说明与日志： 输出必要的来源、有效状态与不确定性；安全日志记录操作和决定，避免不必要地写入敏感正文。

混合检索可以同时利用关键词和语义信号，但不保证天然优于单一方案，需建立业务评测集对比。OpenSearch 官方混合检索说明

8.2 上下文包目标契约

ContextBundle 可包含：请求 ID、任务摘要、主体和租户引用、策略决定或有效性依据、入选记忆 ID 与版本、可访问的来源引用、压缩方式、预算和生成时间。敏感原文只在确有必要且获授权时提供。缓存复用应对权限、来源版本、数据状态及有效期进行复验；策略变动、来源撤权或记忆更新后不得继续盲目重放旧包。

建议采用稳定的排序规则、固定的模型/分词器及明确的截断策略，使同一输入、同一配置和同一依赖版本下的结果可复现；如果调用非确定性模型，必须说明不能保证字节级一致。上下文应区分系统指令、用户请求和来源内容，避免将来源里的指令提升为系统指令。

8.3 降级策略

身份或授权不可验证时默认拒绝敏感信息；索引不可用时可在授权允许且性能可控的前提下查询规范库，或返回明确的受限结果；来源系统不可用时应标记未能复验并按策略拒绝使用受影响内容。降级行为必须有测试和监控，不能悄悄放宽权限。

安全、隐私与信任边界

10.1 身份与授权

目标生产链路应支持可信身份、租户、主体、委派、资源、动作和使用目的的联合决策，按最小权限与默认拒绝实施。策略应覆盖直接 API、后台任务、索引、缓存、导出、管理员操作及外部引擎；跨租户共享需显式设计，不能以猜测 ID 的方式访问。权限在检索前过滤并在结果返回前复验。

历史原型采用签名 JWT 和默认拒绝配置，另有用于演示的签名声明模式；它没有完整的企业策略决策服务，也未证明来源对象真实完整。演示模式不能替代生产权限系统。

10.2 数据库隔离

候选方案以 PostgreSQL 行级安全作为防御层之一：认证后的可信事务上下文决定租户，并在事务内设置必要上下文；应用角色不应是超级用户、表所有者或带 BYPASSRLS 的角色。连接池复用和异常回滚须验证上下文不会泄漏。RLS 不是应用授权、业务对象权限或审计的替代品。PostgreSQL 行级安全文档

历史 SQL 中存在 RLS、角色权限和迁移文件，但历史门禁报告说明未在当时环境对真实 PostgreSQL 执行。数据库隔离是否有效，必须由真实数据库和实际角色测试证明。

10.3 数据保护与提示注入

  • 对传输、备份和静态数据采用符合企业要求的加密及密钥管理；访问密钥使用轮换和最小权限。具体算法与配置须审定。
  • 在模型与检索链中保持可信指令与不可信来源内容的边界；来源内容不得赋予工具、权限或系统指令。对疑似注入的内容隔离、标记或拒绝，并测试攻击变体。
  • 安全日志只记录必要标识与操作结果，敏感内容按政策屏蔽；审计数据自身需要访问控制、保留策略和防篡改机制。
  • 数据分类、跨区域处理、保留和删除按照实际业务、合同与适用法律设计，不能仅靠系统设置自动保证合规。

10.4 审批与高风险记忆

需要审批的内容，应由可信审批系统返回可校验的决定，并绑定请求对象、范围、版本、审批人、时效及用途。系统需要防重放、撤销和权限变化处理。历史快照中的非空 approval_ref 只是格式检查，不提供这些保障。

数据一致性与操作语义

13.1 写入、幂等与并发

同一来源首次登记、版本更新和状态变更应定义事务边界、幂等键作用域、请求指纹、响应重放和键过期处理。并发提交应根据唯一约束、版本比较或受控重试产生可预期结果；过期版本更新应返回明确冲突。历史原型使用版本检查，但首次并发登记同一来源存在未处理冲突，且幂等有效期回收与持久重放状态码存在已知缺口。

13.2 投影、事务事件与失效

目标方案可在规范记录变更的事务中写入 outbox，再由独立工作进程向检索索引、缓存或外部适配器传播。消费者应具备幂等处理、重试、失败隔离、进度与延迟监控，以及可重建与对账能力。事务写入 outbox 不等于消息已经送达；一致性延迟及失败处理必须明确。历史快照有 outbox 表和事件写入，没有完整的投递、重放或死信工作进程。

可使用版本、代际或不透明票据关联投影与来源变更，但语义、冲突处理及恢复均需要实现和实测。读取时复验权威状态以降低过期结果风险。

13.3 来源真实性

来源 URI 前缀允许列表只说明地址满足配置规则，不能证明调用者有权读取对象、对象存在、摘要真实或内容未变。生产接入须由可信连接器访问对象并验证版本、哈希及来源权限；对不可验证的来源按政策拒绝或隔离。具体信任链由对接系统共同定义。

17.2 修改流程

  1. 为每个主题指定负责人；新需求先检查现有内容和决策，尽量更新唯一源，不复制一篇同题文档。
  2. 明确本次变化属于已批准方向、目标设计、接口契约、实现状态还是测试证据；不要因版本号为 V1.0 就把草案自动升级为已批准。
  3. 涉及兼容、安全、数据边界或供应商选择的变化，建立简洁 ADR：背景、备选项、决定及状态、影响、验收、关联版本。状态可用 Proposed、Accepted、Superseded；批准者和日期必须真实。
  4. 在同一变更中更新对应源文件、受影响的接口/测试链接及本入口，重新生成 HTML；发布前由责任人检查引用、状态、链接与图示。
  5. 保留旧资料和关联证据，标明历史或已替代；迁移、删除或归档应按实际保留政策执行。本次没有移动或删除旧资料。

17.3 本交付物的维护方式

配套维护包提供本入口的 Markdown 唯一正文、离线生成脚本、必要字体与第三方许可，以及历史接口/模型快照。维护者修改唯一正文并运行构建脚本即可重新生成 HTML；不要同时手工维护两套正文。若更新超出已包含字体的字符，需按维护包说明重新生成字体子集，否则浏览器将使用本地后备字体。本文中的历史快照是证据，不自动成为正式发布契约。
