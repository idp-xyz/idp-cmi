IDP CMI 白皮书全球技术对照与评审报告

评估对象：《IDP CMI 企业上下文与记忆基础设施白皮书 V1.0 Draft》
评估日期： 2026-11-04（北京时间）
评估性质： 产品与技术设计评审；不是源码安全审计、性能基准或生产验收报告。

1. 结论

**总体判断：CMI 的独立定位和数据治理方向成立，白皮书是一份较好的架构讨论稿，但距离可执行、可验收的企业级产品规格仍有明显差距。**不需要因全球技术发展推翻 CMI、HOST、EER、MCP 和业务系统已经明确的责任边界；应围绕记忆治理、跨范围授权、可解释检索、业务评测及工程闭环继续细化。

白皮书已有可信来源、版本、作用范围、撤权、候选记忆、可替换引擎、基本质量指标和阶段路线。当前缺口主要是这些概念怎样在真实身份体系、数据链路、模型调用和失败情况下执行并验收。

本报告将文本成熟度主观评为 6.6/10。这个分数是八个评审维度的等权平均，帮助定位文档缺口，不是国际基准、产品性能分数或对任何产品安全性的认证。CMI 产品实现与生产成熟度不打分：本次未审计新的代码仓库、运行中的数据库或部署环境。

2. 评估边界与证据

  1. 当前评估依据是该白皮书 2026-11-04 可读取的当前版本；按其章节定位发现的问题。原文将既有设计、提案及原型状态分开，本报告沿用这一边界。
  2. 外部对照覆盖云平台与开源项目的官方文档、2025–2026 年论文、正式会议研究和安全研究。在线文档可能随版本变化；实现前应重新检查具体版本、地区、部署方式、许可和服务条款。
  3. 官方文档只能证明其公开描述的能力，不证明 IDP 适配可用或具备相同的隔离、安全、吞吐和成本。
  4. 研究论文的实验分数受数据、模型、提示、裁判、检索范围和成本设置影响，不能直接排名不同产品，更不能当作 CMI 的实测结果。特别标记的 2026-10-29 论文为预印本。

4. 全球技术对照：哪些值得借鉴

4.1 云平台与开源产品

项目 官方资料显示的相关能力 对 CMI 的启示与限制
Google Memory Bank 按 scope 提取并整合记忆，支持新增、更新、移除；也可对提供的候选进行整合；另有基于 scope 的 IAM 条件。 S1 S2 应具体定义抽取和整合操作；scope 应与真正的授权策略共同工作。托管产品的自动处理并不证明适合直接更改企业正式规则。
AWS Bedrock AgentCore Memory 使用 memory strategy 和带 actor、session 等变量的 namespace 组织长期记忆。 S3 层级命名便于组织，但 CMI 仍应独立判定主体、委派、资源和用途，不能把字符串路径本身当作完整授权。
Microsoft Foundry Memory 文档描述受管记忆存储和单条记忆管理；当前页面标明 preview。 S4 显示跨会话记忆已成为平台能力；预览状态、部署区域和条款需按实际版本核对。
Mem0 当前官方 main 文档区分开源 SDK 和托管平台，描述 add 时可抽取记忆，并以用户、Agent 等标识限定后续搜索。当前文档将该写入流程描述为追加式。 S24 适合作为可插拔对照；不能只凭产品名称就假设 add 一定自动合并、更新或删除，也不能把作用域标识当作企业完整授权。实际行为应按固定版本测试。
Letta 当前产品文档描述使用 Git 跟踪的 MemFS 和后台整理；其旧版 V1 SDK 文档也提供可附加、只读或可写的 memory blocks。 S5 S25 可借鉴分层加载和后台整理；需区分当前 MemFS 与旧版接口，不将旧版默认配置外推至新版本。企业制度和个人隐私仍需要受控写入。
Hindsight 提供 retain、recall、reflect 三类核心操作。 S6 CMI 应区分“存储候选”“检索依据”和“生成反思建议”；反思结果不能直接升级为权威事实。具体引擎只作可替换 PoC。
Zep / Graphiti 使用来源 episode、实体、关系和时间信息组织 context graph；官方明确来源关联不保证事实正确。 S7 增强实体关系和历史检索有价值，但图谱不是权威账本，是否引入须由多跳问题和成本验证。
OpenViking 使用 L0 摘要、L1 概览、L2 原文的分层上下文组织；当前主仓库说明主项目采用 AGPLv3，部分组件许可不同。 S8 S9 可评估按需展开和层级导航；摘要必须继承来源和权限约束，实际商用依赖的许可证应按锁定版本审查。
OpenSearch Agentic Memory 提供 memory container 与记忆接口；3.8 引入的 retention 页面标为 experimental、不推荐用于生产。 S10 S11 可做检索和记忆能力 PoC；不能仅依赖该实验性 retention 达成企业级删除或保留承诺。
PostgreSQL + pgvector 可通过 FTS 与向量能力组合；近似索引与过滤、多租户共享索引存在召回和性能取舍。 S12 维持现有参考路线，按租户和过滤选择率对比精确检索、近似检索及索引策略；尚无依据锁定最终生产选型。

**不要从上表推导“CMI 已领先”或“应该替换成某个产品”。**这些项目的产品目标、开源与托管边界、默认配置和评价场景不同。对于 CMI，企业范围控制、来源/生命周期主权和可替换接口可以成为差异化方向，但价值必须用真实业务和同条件实验验证。

需要特别更新的一点： Mem0 当前官方 main 文档将 add 流程描述为新增记忆，不在该流程中覆盖或删除现有记忆；关闭推断时可能产生重复。它的过期内容也并非所有读取方式都自动不可见：文档注明按 ID 获取仍可能返回过期内容。这个描述针对当前文档，不代表所有历史版本或全部托管功能；CMI 必须按固定组件版本验证更新、过期、按 ID 查询及删除行为，不能把供应商接口当作完整生命周期政策。 S24

4.2 2025–2026 年研究的启示

  1. **记忆不应只有一种表示。**ACL 2026 的 APEX-MEM 将带时间的事件、关系结构与检索时处理结合。2026-10-29 的一篇预印本研究情景记忆、结构化关系与离线整合的组合；其结果限于论文中的对话数据、模型与设置，不能外推为企业必然收益。CMI 应保留情景与关系的表达能力，但无需因此把图数据库变成首版强制依赖。 S13 S14
  2. **评测需要覆盖 Agent 工作过程。**LongMemEval 面向长期会话中的提取、多轮、时间、更新和拒答；ICML 2026 的 AMA-Bench 进一步讨论状态、动作、观察和工具输出组成的长程轨迹。它们补充了现有白皮书 §14 的指标列表，但均不能直接替代企业授权和真实流程测试。 S15 S16
  3. **安全评测需要贯穿写入、调用和清理。**OWASP 将 Memory & Context Poisoning 列入 Agentic 应用风险；MemoryGraft 研究通过污染历史经验影响后续行为，MemSecBench 研究持久化、下游后果与修复。应对 CMI 建立从恶意输入到消费、撤销和恢复的完整测试，不只做单次提示词过滤。 S17 S18 S19

5. 白皮书中值得保留的设计

5.1 不强制业务系统或 HOST/EER 依赖 CMI

§3 和 §11 明确 CMI 可以独立服务，也不接管业务事实、EER 执行结果或 HOST 会话。这个边界适合企业逐步接入、隔离故障和使用第三方组件；新能力应在此基础上增量建设。

5.2 区分权威来源、记忆、推断和建议

§5.3、§7.4 和 §8 已强调来源、有效时间、事实与模型推断的区别。它与 Zep 官方对 provenance 的提醒一致：找到来源能够支持溯源，但并不能证明内容真实。 S7

5.3 规范账本与可替换投影

§10 使用事务 outbox 和可重建投影，避免把搜索索引或外部记忆引擎作为唯一权威来源。这个方向适合应对版本变更和引擎替换；仍需用真实数据库、故障注入和安全测试证明实现。

5.4 不预设图谱、OpenSearch 或某一记忆引擎为默认底座

对照研究中既有简单检索、层级上下文、自动整合，也有时序图与 agentic retrieval；没有证据支持一种方案在所有企业场景、权限过滤率和成本预算下最优。白皮书保留选型空间是合理的，但后续必须设计对照实验，不能长期停留在“可选”。

6. 关键问题及改进建议

优先级说明：P0 是进入受控企业试点前应定义并验证的基础边界；P1 是基础闭环稳定后应补充的产品效果和可操作性；P2 是需要由场景和数据证明收益的增强。这里的 P0/P1/P2 是本次评审建议，不自动改变既有产品决策或排期。

P0-1：把单一 scope 扩展为可验证的授权模型

原文位置： §6.1–6.2、§9.1。白皮书正确说明范围不等于权限，但还没有定义组织结构、资源关联、委派和成员变化如何共同决定一次访问。历史原型只提供单范围查询及 PoC 策略，不能据此认为多范围治理已实现。

建议： 将以下概念分别建模：

  • 租户 tenant：隔离边界，由可信身份上下文确定；客户端输入不得自行决定。
  • 请求主体 actor：真实用户、工作负载、代理，以及被代理人的委派链。
  • 资源及归属：记忆所属范围、项目/业务对象关联、陈述主体与来源权限。它们相互关联，但不能用一个字段互相替代。
  • 操作与用途：查询、写入候选、修改、共享、批准、失效和删除分别授权；用途可限制读或外发。
  • 当前策略：用户当前成员资格、分级、授权及撤销结果。历史有效时间不能自动恢复已撤销的查看权限。

逻辑上，一次读取至少需要满足可信租户、主体/委派、操作和用途、记忆资源，以及为该陈述提供必要证据的来源授权。多范围查询必须先得到当前允许范围，再对具体结果复验；不能以“属于同一企业”或“路径匹配”替代资源授权。

验收例： Alice 和 Bob 属于同一个租户及项目；Alice 的私人偏好不能因为共同项目而返回给 Bob。Bob 离开团队后，即便旧 JWT 或缓存仍在，后续获服务端确认的撤权也应在承诺的边界内阻止新请求读取。测试应覆盖用户、代理、系统服务、离职、转组及项目授权变更。

P0-2：明确来源依赖和派生记忆的权限传播

原文位置： §6.2、§7.3、§9.3。原文已提出合并内容不应放宽必要来源的权限，但缺少到“具体陈述—来源版本—摘要/向量—上下文包”的追踪粒度。

建议： 为每一条可返回的陈述建立来源版本及派生关系；记录摘要、合并结果、embedding、索引及 Bundle 引用了哪些对象。涉及多个必要来源时，默认使用不弱于所有必要来源的权限；若不同来源是独立的替代证据，可仅返回被授权且足以支撑该陈述的分支，但需要逐条可验证，不能通过汇总暗示不可访问的来源。

来源撤回或权限变化时，沿依赖关系使受影响的派生结果失效或重算；不要把“有 provenance”误写成“事实已证实”。

验收例： 一份摘要同时依据部门公开文件和 Alice 的私人对话生成，Bob 只能访问前者。不得向 Bob 返回包含私人信息的整条摘要；若要提供公开部分，应能证明该部分独立来源及权限，并重新生成或提供相应片段。

P0-3：把记忆投毒扩展成全生命周期安全控制

原文位置： §8.4、§16.1。原文识别了提示注入和记忆污染，但未规定攻击进入、被抽取、被合并、被召回并影响工具行动时的逐阶段控制与修复。

建议：

  1. 把外部文档、聊天和工具输出标为不可信数据，显式记录来源和发布主体；不要把检索内容提升为系统指令。
  2. 模型抽取、相似判断和反思只输出受约束的候选与证据；不能自行授予高可信来源、组织共享权限或正式审批状态。
  3. 高影响组织规则、跨范围共享和危险的程序性经验需要独立权威验证与适当审批；一般个人偏好可由风险策略决定是否自动处理。
  4. 在模拟业务场景中验证恶意记忆被召回后仍不能绕过现有工具授权和 EER/业务系统的责任边界。
  5. 对被污染记忆执行范围确定、阻断、派生内容清理、受影响 Bundle 标记、重放/恢复验证，并记录误删及恢复影响。

验收例： 某低可信来源伪装成“过去成功的客户操作经验”，诱导 Agent 调用未授权工具。测试必须覆盖写入、检索、模型使用、实际操作被拒绝及污染清除；不应只测提示分类器是否报警。研究与威胁分类为设计测试提供依据，不保证任何单一防御有效。 S17 S18 S19

P0-4：定义撤权、擦除和模型外发的真实边界

原文位置： §9.3、§10.2、§13。同步屏蔽和异步清理方向合理，但没有规定撤权从何时算生效、处理中请求如何处理，以及已发给外部模型的数据是否可撤回。

建议：

  • 将“权威策略系统确认撤销并使 CMI 读屏障生效”的时点定义为可测试的起点；分别记录新查询阻断、索引净化、外部引擎确认、备份策略处置的时间和状态。
  • 在检索、Bundle 返回和敏感内容送入模型前按约定检查当前授权及策略/资源版本；仍需承认跨系统调用中的竞态。
  • **已交付给调用方或外部模型的明文不能由 CMI 单方面收回。**模型服务的保留、删除和再利用能力须由供应商配置与合同/技术控制另行验证。
  • 擦除操作跟踪各目标域的待处理、成功、失败和例外；完成状态只覆盖实际已验证的范围。备份依单独策略轮转，恢复时重放屏障，不能承诺即时物理擦除所有副本。

验收例： 撤权发生在检索后、模型调用前；测试策略变更、Bundle 校验、传输取消及日志脱敏。另测内容已发出后的报告应诚实标注“无法由 CMI 撤回”。

P0-5：从候选状态变更补全真正的记忆更新事务

原文位置： §7、§10、§15。已有 PR-01～PR-03 原型说明包含候选及状态转换；但状态转换不等同于完成“新陈述与旧陈述对齐、创建新内容版本、来源验证、冲突处理和回放”。PR-03.1 还记录首次并发来源写入等缺口。

建议： 为 propose → compare → decide → commit → project 定义明确输入、输出、授权主体、预期版本、幂等键、事务内容、失败码与追踪证据。审批引用需由可信审批服务验证，而非仅检查非空字符串；来源对象的存在、内容摘要和权威性按策略验证。

规范提交与 outbox 事件需原子化；相同请求重试不产生重复效果，同一键携带不同请求时明确冲突。旧版本投影和重复事件不能重新激活已撤销内容。具体 SQL、重试和应用角色需在真实 PostgreSQL 中测试。

验收例： 两个写入者同时为同一客户创建相同来源；一个成功后另一个返回明确冲突或按设计安全重试，不能出现未处理 500、重复来源或丢失审计。模拟事务回滚、队列重复、乱序、断电和恢复。

P1-1：把记忆优化从概念变成可操作协议

原文位置： §7.2–7.5。现有生命周期方向完整，但 ADD、去重、更新和冲突缺少条件、结果与操作责任。Google 的文档可用来理解 scope 内整合和版本管理，但其自动化行为不等于 CMI 的企业治理策略。 S1 S20

决策结果 适用条件示例 最低记录与限制
新增候选 合法范围内无等价陈述，来源有效 来源版本、范围、抽取方式、用途、风险类别
保持不变 与现有内容等价，且范围、时间和语义一致 记录判定结果及新增来源是否被接受
合并候选 只合并同一授权范围且含义、时间相容的重复内容 逐来源依赖、权限与可撤销关系；有歧义进入复核
建议替代 新的有效信息与旧内容有明确替代关系 原有版本、权威来源、有效时间、决策者与审批依据
标记冲突 无法判定哪个来源/时间具有权威性 保留双方依据和冲突状态；不能静默覆盖
停用或删除 策略、撤权、到期或受控擦除要求 区分停止使用、历史保留和物理删除

上述名称是逻辑操作，不声称现有 API 已实现。优化应分同步路径和后台路径：低风险偏好可在策略允许时自动提交；企业正式规则和高影响程序性记忆必须依赖经过验证的来源/审批。周期性聚合、反思与查询时整理都应有成本、权限和质量边界。

关键案例： 用户先说“报告先列明细”，后说“技术报告先给结论”。系统不应简单判定全部偏好反转；应保留适用文档类型与时间，有歧义时要求确认。

P1-2：定义检索路由、上下文预算和拒答

原文位置： §8.1–8.2。方向正确，但需要从“可以综合考虑”进一步定义查询类别和结果不足时的行为。

查询 建议路径 必须验证
运单号、渠道代码、合同号 规范化后的精确标识检索 命中精度、权限、不同租户同号冲突
中文业务表述和近义词 全文检索，必要时加语义召回与融合 中文分词、缩写、拼写、来源和语言分布
历史变化/关系问题 版本和有效时间过滤，按需关系查询 新旧冲突、记录时间与业务时间、来源撤回
多来源复杂问题 在授权候选内分解、检索、重新排序 调用次数/成本上限及引用覆盖；不能把无权限信息传给 reranker
证据不足或来源不可用 返回缺失、冲突或需要实时核实 不用相似但未经验证的记忆填补答案

近似向量索引遇到强过滤可能召回不足。应在相同授权数据集内，以精确检索结果为基线，按过滤选择率报告 Recall@k 和时延；并评估迭代扫描、分区或其他方案。数据库执行计划可能在 ANN 扫描后应用过滤，安全上不允许未授权结果返回或传入模型；检索内部实现的过滤顺序还必须单独评估召回与侧信道。 S12

ContextBundle 应区分事实来源、历史案例、冲突信息、偏好和建议；对必需内容无法装入预算、当前来源不可访问、策略版本改变、部分索引滞后分别给出可处理结果。消费者收到信息之后仍自行承担复验及执行责任。

P1-3：建立企业任务与公开基准结合的评估体系

原文位置： §14。已有质量与安全指标，但还缺少数据分层、固定对照、标注和运行证据，不能直接得出 CMI 的优势。

建议分四层：

  1. 基础不变量： 权限、跨租户、时间状态、来源有效性、幂等、并发与删除，不依赖模型评分。
  2. 公开任务： 可用 LongMemEval 测试多轮、时间、更新与拒答；借鉴 AMA-Bench 测试状态、动作、观察与工具轨迹。只报告实际完成的基准和设置。 S15 S16
  3. 安全任务： 在受控环境设计污染、共享范围越权、撤权、模型外发、失效恢复与精确修复任务，参考 MemoryGraft / MemSecBench 的问题定义。 S18 S19
  4. IDP 业务任务： 经授权、脱敏的 Parcel/Brant 案例覆盖地址异常、渠道规则、客户偏好、跨员工信息、旧合同与新合同冲突、错误建议纠正。业务系统结果仍由其权威记录确认。

对照组至少包括：无长期记忆、当前基础文本检索、相同语料上的混合检索，以及通过安全门的可选引擎；控制模型、提示、语料、预算和硬件。统计效果、来源正确率、未授权返回、过期引用、成本与延迟；保留匿名化样本 ID、运行配置、模型/索引版本、日志和原始结果。

避免把供应商提供的 LoCoMo/LongMemEval 排名直接混用：语料版本、是否包含原始 episode、问答模型与 judge、失败处理和 token 预算不同，会显著影响可比性。

P1-4：明确观察性、可复现与责任界面

原文位置： §8.2、§13–14。原文已经说明 Manifest 哈希不等于证明模型实际输入，但还需要定义边界内可证明什么。

建议为每个上下文请求记录经过脱敏的 request/trace_id、主体/委派引用、策略与来源/记忆版本、检索策略、模型与 tokenizer 配置、预算、被省略原因以及失败状态；是否保存原文由政策决定。对历史重放分别标识“重建引用清单”“在允许保留内容时重建字节”“尽力重现语义”，不能用同一个“可重放”概括。

CMI 可以证明自身形成的清单及接口返回；HOST 或其他消费者负责证明其实际发送到模型的内容和后续行为。外部模型如何处理、保留或删除数据，需要独立合同与技术证据。

P1-5：补充多客户端接入和协议一致性验收

原文位置： §11.4。保留 CMI 独立 API 以及可选 MCP 适配器的方向，不把 MCP 网关变成 CMI 的强制依赖。MCP 官方 2026-07-28 规格说明无状态协议内核、按请求携带版本和路由信息，与 IDP 已有现代协议基线一致；是否支持某项扩展及具体 SDK 版本，需要在实际适配时验证。 S22

建议使用同一套 CMI 领域与资源授权契约处理 REST 和可选 MCP 调用：传输成功或客户端自报身份不能代替用户/代理委派和记忆授权。协议无状态也不意味着业务上下文不需要显式标识、版本和权限；不能把协议会话当成唯一的用户或租户隔离边界。验收应覆盖同一请求经不同入口结果一致、越权 ID 不泄露、撤权后缓存及工具目录使用，以及 CMI 在 MCP Infrastructure 未安装时独立运行。

P1-6：为个人、业务负责人和管理员设计可操作界面

原文位置： §6–7、§9。现有文本说明了范围和治理原则，但尚未定义用户怎样查看、纠正、共享或停止使用记忆，也没有界定不同管理角色能看到什么。

建议为获授权的个人提供记忆查看、来源说明、纠错、共享申请与删除请求；为业务负责人提供组织规则候选、冲突复核及经授权的批准入口；为管理员提供范围策略、系统状态和按权限脱敏的审计。管理某一组织不应自动意味着可以读取全部员工的个人记忆，具体权限仍由企业及适用政策确定。删除申请的接受、阻断和完成是不同状态，界面应明确展示，不能仅因为已提交就显示“已全部删除”。

P1-7：为部署基线补充安全补丁与持续扫描

原文位置： §10.3、§15。白皮书已引用 PostgreSQL CVE-2026-14666，指出 PG 16 从 16.15 起修复特定 RLS 缓存问题；应保留这一准确限定。后续应在实际依赖清单中记录镜像摘要、数据库和扩展版本、角色与连接池设置，结合官方公告持续核查并验证升级与回滚。是否受该 CVE 影响取决于具体配置，不能依据白皮书推定现有部署存在漏洞。 S21

7. 围绕组织和个人记忆的完整示例

场景： 企业 A 的客户服务团队处理客户 C 的渠道异常，员工 Alice 查询；同团队 Bob 可以查看客户公开规则，但不能查看 Alice 的个人偏好。以下均为示例数据。

信息 建议范围 来源和处理
客户 C 的正式渠道规则 经授权的客户/组织范围 来自权威配置或已批准制度，带版本和生效时间
过去一次面单失败及处理 客户或业务对象范围 来自对应 Parcel 事件或经核验的处理记录
Alice 喜欢先看结论 Alice 的个人范围 来自 Alice 的明确表达；不可因团队共享被 Bob 读取
模型推断“客户总是选择 UPS” 待验证候选 不能自动当作正式渠道配置

读取： CMI 先验证 Alice 当前身份、组织及客户权限；在合法范围检索规则、历史案例和个人偏好。当前发货字段及渠道配置通过授权业务来源核对。若正式配置源不可用，返回“当前状态未核实”，不将历史案例替代当前事实。

变更： 客户规则发生变化时，权威来源的版本/事件或责任人已验证的提交产生新候选；系统检查生效时间与旧记录的关系并依政策处理，保留必要的历史引用。用户仅说“我觉得好像变了”不应直接覆盖组织规则。

撤权： Alice 离开团队后，后续受控查询不应返回她已失去权限的客户数据；她的个人偏好如何保留或迁移由租户及个人数据政策决定。对于此前已经发给外部模型的数据，CMI 只能依据已配置的供应商能力跟踪，不能单方保证撤回。

8. 路线建议：保持现有基线，补齐可验收闭环

建议顺序 工作 退出标准示例
1 固定当前原型、契约和历史 QA 证据；执行数据库安全 Gate 并修复已知并发/幂等问题 真实数据库的迁移、RLS、角色、并发和失败测试可复验；历史未测试项目不再以假设填补
2 明确组织、个人、主体委派、来源授权及共享/撤权模型；对接可信策略和审批/来源接口 多租户、多主体、多范围、转组与撤权负向测试通过
3 完成受控记忆决策、来源依赖、语义版本与删除屏障；实现并验证 Context Compiler 基础闭环 新增、等价、冲突、替代、失效、拒答和 Bundle 复验有可追踪证据
4 建立真实业务评测集和公开基准对照；逐步评估混合检索、模型抽取和可选记忆引擎 效果、延迟、成本、注入攻击和来源正确性在同条件下报告
5 针对复杂关系问题测试图谱、分层上下文和反思，形成保留/替换决策 增量收益、迁移、删除、隔离及运维成本可量化，且不改变独立边界

可以按依赖关系并行准备规格、样本和连接器，但安全和数据正确性不足时不能用“先进”或公开排行榜替代验收。
